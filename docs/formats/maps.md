# Maps: chunk lists and Borg9 (roadmaps 1C and 1E)

A map set is a grid of chunks, and each chunk is a Borg9 (collision, its grid and the map objects) plus up to two Borg5 scenes.

## Map objects (1E)

1E reads only the map objects of each Borg9, since they're what gate on flags and start dialogues. The rest of Borg9 is 1C's. The original's own name for them is voxel objects: the ROM's crash and debug strings name `RenderVoxelScenes` (in all three ROMs), and `GetVoxelObjectFromLink`, `ProcessVoxelObjects` and "Invalid Voxel Object for trap" (in the debug ROM). The decomp took the word from these, and their record IDs keep it (`aidyn:voxel/…`).

- **Map chunk lists** are 17 zero-terminated lists of 12-byte entries (row, column, scene, alternate scene, Borg9, terrain), back to back in the code segment. They're at `0xDBD90` in 1.0, `0xDBDD0` in 1.1 and `0xEA850` in the debug ROM, identical in all three: 543 chunks. 57 Borg9s aren't in any list.
- **Map objects** are 0x6C bytes: a 0x28-byte header (position, radius, a run-time time stamp, flags, type, two links, flags A, B and C, and a run-time pointer), then 0x44 bytes that depend on the type. The Borg9 header's count and pointer at 0x28 and 0x44 find them, and the collision sections start right after, 8-byte aligned. There are 26,091 across 584 Borg9s.
- **The three flag slots.** A flag check is the flag's value XOR an invert bit, where flag 0 is always false and flag 1 always true, so an inverted 0 means "always".
  - **C** (inverted by bit 0x80) says whether a scene, light, sound, teleporter or trigger is there at all.
  - **A** (inverted by 0x100) says whether a teleporter, trigger or dialogue works, and whether a monster party is there.
  - **B** is written when the object is used: set, or cleared if bit 0x200 is on. A monster party without a dialogue is gone while its B is set, and winning its fight sets it. With a dialogue, talking to it sets B. A dialogue object's B always equals its script's done flag (273 of them; 91 are 0) and the game doesn't read it.
- **Type-specific flags:** containers have an "opened" and an "exploded" flag; teleporters have lock, unlock, trap, disarm and secret-door flags.
- **Dead writes:** the game only writes plain flags from 2 up. Two SetFlag triggers name derived flag 5495 and flag 0, and six monster parties name derived flags as their B.

## Collision, the grid and placement (1C)

`Borg9Map` reads the rest of each Borg9: its collision and the grid that indexes it.

- **Layout.** A 0x50-byte header, then six parts, each 8-byte aligned: the cells' triangle indices, their object indices, the vertices, the triangles, the map objects and the cells. The header holds the counts of each and their offsets from the start of the data. Two of its offsets (0x30 and 0x40) are fixed up by the game and never used, and hold leftovers. Byte 0x1B, after the u16 count of the cells' object indices, is a bit for each neighbour the zone engine draws whatever the camera's view while the player is in the chunk, imported as the map's `DrawnNeighbours` ([rendering](../systems/rendering.md#scrolling-textures)); 22 Borg9s set it. Byte 0x1A varies too, and isn't known. All 584 Borg9s match this exactly. 24–48 bytes follow the cells, all zeros except in one file.
- **Triangles** (168,317) are 0x20 bytes: three vertices as byte offsets into the vertex list, a unit normal, a surface, flags and a ground type. They wind counter-clockwise about their normals, except for 27 with no area and 19 slivers.
- **Surfaces** are the 26 physics properties the game names in `String/Common`: Default, Collision Player And Camera, Collision Player, then footstep materials such as Grass, Stone and Water, and "Trans" versions of each. The data uses 19 of them. Most walls and floors are *Player And Camera* (101,394). *Player* (10,345) is for invisible walls: all of them, and only them, have flag 0x200, which line-of-sight tests skip, so the camera passes through. Whatever touches those two surfaces keeps its speed and slides along; every other surface stops it (`EnvPropBools`). Water has a speed property that halves speed and nearly cancels gravity, but no triangle has flag 0x2, which applies it.
- **Flags** say which edges and corners collide, besides the face. The decomp's edge bits are right: the data confirms it, since every edge no other triangle shares has its bit (0x4 is A→B, 0x10 is B→C and 0x8 is C→A). No triangle is passable (0x1) as stored.
- **Ground types.** The top four bits give a triangle's role, and the game rewrites the rest when it loads the chunk:
  - 160,474 are ordinary.
  - 1,849 are **triggers**: the low bits index a map object, which runs when the player walks on the triangle. 1,532 name cameras and 317 name dialogues.
  - 62 are **toggles**, with an id one more than the low bits. A `ChangeCollision` trigger that names the id makes them passable, so the way opens. Every toggle id has its trigger in the same Borg9, and every such trigger has its triangles.
  - 5,932 are **Expansion Pak only**. Without the pak, the game makes them passable.
- **The grid** starts at the collision's minimum corner, with cells about 5 units square. Each cell lists the triangles near it, and the objects the player could use from it or that it draws: scenes, containers, lights, teleporters, cameras, dialogues, triggers and the three save points. Sounds, wander nodes, monster parties and reference points are handled per chunk. A weighs only the objects the cell under the player lists (`obj_ref_func`), so the lists are imported as each map record's `grid` (importer 18). On the grid, every cell an object's reach covers lists it. `getZonePositionShorts` finds the cell by truncating toward zero, so up to a cell before the grid's start counts as its first column or row, and a point off the grid either way counts as cell (0, 0), as the US 1.0 machine code shows. So beyond its collision's extent, a chunk's objects are out of A's reach unless the first cell lists them. One dialogue, `aidyn:voxel/0x185C/0`, is off its map's 3 × 3 grid altogether, so A never reaches it. 26 triangles, in 8 Borg9s, are in no cell, so nothing collides with them. Chaos Isle's A09 (Borg9 5019) has a 1 × 2 × 1 box of 8 triangles about 297,000 units away. It stretches that chunk's grid to cells 12,383 units wide, so the rest of the chunk sits in one cell. It still works, but every collision test there checks every triangle.
- **Map objects, the rest of the types.** Scene objects place 1 or 2 levels of detail of a Borg5 (7,913), a Borg7 actor (163), or a container's model followed by its opened and destroyed models (371). They scale, then rotate, then move, and rotate by `guRotateRPYF` with roll = `rot.x`, pitch = `rot.y` and heading = `rot.z`, in radians. That's not the Borg5 transforms' order (they swap X and Y); the machine code confirms it (`Scene::MatrixARotate` passes its first two angles to `guRotateRPYF` the other way round, and the call site in `RenderVoxelScenes` passes `rot.y, rot.x, rot.z`). Lights hold two colours and a way of moving between them (static, alternate, sine, random). Sounds play a Borg12 with a volume and a random wait. Wander nodes form chains, each naming the next two. Cameras move the camera or its aim to a reference point (or above the player) by cutting, panning or easing in three ways, or set how far behind and how high the outdoor camera follows; the import names those flags (importer 19, see [cameras](../systems/cameras.md#camera-objects-processvoxelcamera)). The code objects and save points hold nothing.
- **Chunks in a set.** A chunk's own coordinates start at (row × cell size, 0, column × cell size): rows run along X. The cell size is a literal in `BorgMaps::LoadMap`, checked in 1.0's code: 100, except 500 for the misc interiors, 30 for Erromon, 200 for Terminor, 25 for the Barrows, 1000 for Ehud's tower and 150 for the battlefields. Neighbouring chunks' collision overlaps by 10–30 units, and a test confirms the placement: where it overlaps, 95% of the overworld's ground heights agree, against 3% with rows along Z.
- **A chunk's second scene** is drawn after everything else (`renderTransZones_`), so it holds see-through surfaces such as water. It isn't an alternative to the first.
- **Chests mostly face one way.** Of the 179 chests with a collision box within reach, 134 aren't turned at all and 45 are, such as the one beside the player at the start of the game (I08, turned 36°). The collision was baked from the same placements, and the boxes line up face for face with the models as the game rotates them. That includes all 11 chests that are knocked over, which settles the rotation's axis order without the machine code: Borg5's order gets 9 of them wrong. One box is 2° off its model, and 12 chests stand against other walls, so the check can't tell for those.
- **Reference points** mostly sit in clusters, which the user recognised as where cut-scenes put their cameras.

## Map objects in the base plugin (0.6)

The importer writes every map object but the code objects into its map's record, one type each (`MapRecords.cs`). What each field means is in the records' comments; what the import found is here. Checked in 1.0's code where it says so.

- **Which flag slots each type reads** comes from the "is it there" functions (`gVoxelFuncs2`) and the use functions (`gVoxelUseFuncs`), checked in 1.0's code. Lights, sounds, wander nodes, reference points, cameras, scenes, teleporters and triggers are there while C holds. Monster parties are there while A holds, and without a dialogue, while B is clear. Dialogues and save points are always there. Chests, sacks, crates and barrels are there until opened or destroyed, and herb, spice, gem and custom containers are gated by A and C. A record leaves out the slots its type doesn't read, and flag B where it's 0.
- **Header bits.** 0x8000 (active) is only ever set at run time, from the gates. 0x2000 (tangible) matters for teleporters, triggers and dialogues, which go off when walked into; a tangible teleporter skips its secret, trap and lock. 0x400 marks what the player can reach to use. 0x4000 is set on most scenes, containers, teleporters, triggers and dialogues, and on no other type; nothing is known to read it. Lights' 0x1 (25 of them) is unexplained too. Neither is imported.
- **Links.** Both link slots always hold the same index, and the game only reads the first. To find a container's model or the actor a trigger animates, `GetVoxelFromObjectLink` follows links from object to object until it reaches the type it wants, up to 51 steps. The decomp reads it as scanning the first 51 objects, but the code follows the links. Every container reaches its scene, and every Animate trigger an actor. Code objects all link to object 0.
- **Containers.** The trap's level is at +0x0E and the word before it is its state (0 while armed, 0xFF once disarmed or set off), which the decomp names the other way round: `TrapMenu::GetTrapLV` returns +0x0C and the menu reads the level from the word after it. The state is 0 in all the data. The lock's level is the u16 at +0x14. A loot table is found by `GetIDIndex`, which for a potion's ID returns its low byte, so the two containers in Borg9 0x10F5 whose loot names a potion roll the loot table at that position, and the import names that table. A monster party's loot can be a single item. **A container's reach** is the float at +0x04 (`chestSize`), which the decomp says "seems identical to" the header's radius; it isn't. 222 of the 377 containers have a radius of 10 and a reach of 2, and the reaches run from 1 to 5. The word at +0x00 is a copy of the radius. `container_obj_check` uses the reach, plus the player's scaled radius, and nothing reads the radius for containers; the user found the start chest opens from about 2 away, facing any way (Oct 1, 2026). Imported as `ContainerObject.Reach` (importer 18).
- **Teleporters.** The trap's level is at +0x0A (the word before it, at +0x08, is its state), and a reference point for the camera at +0x0E. Any secret flag but 0 and 1 makes a door secret, whatever its level, which is 0 in all the data: using it while the flag is clear shows "secret door" and sets it. The eleven in EhudUnder C11, E03, E11 and I09 are the only ones, and they set eight of the checkpoints' flags 1E had no setter for (see [hardcoded-content](../hardcoded-content.md)). The arrival and camera points are found by ID in the destination chunk's map, 0x7FF8 meaning the teleporter's own position, and the import names them by voxel ID. Five teleporters into Jundar's interiors A01 name camera points it doesn't have, which the original ignores. One of them, patioL2 in the Jundar interiors K07, also names an arrival point it doesn't have, which the original would read through a null pointer.
- **Monster parties.** +0x28 and +0x2A are the battle's least and most enemies, and +0x2E the home wander node, which must be a moving one. +0x24 is filled in at run time. Flag 0x4 on the party makes talking to it do nothing though it has a dialogue (checked in 1.0's code), so it never sets its B or starts its script. The 15 silent parties are the people in staged scenes: Arturo, Baird, Donovan and Rheda back in Terminor, the troll at the bridge ("Halt yurrr walkings"), Sheridan in Gwernia Castle, a dryad calling "Wait, human child!". A dialogue object, mostly a tangible one the player walks into, starts 13 of their scripts, and the party is the body standing there, which pressing A on would otherwise start again. The other two (Arturo's "I have nothing to say" and Keelin's "new in town?") nothing starts. Flag 0x2, on 990 of them, makes the party walk to its wander nodes rather than run ([wanderers](../systems/wanderers.md)); the decomp reads it as the node's. With a dialogue, flag C is the battle's encounter flag if the dialogue fights.
- **How a fight starts:** a party without a dialogue chases the player and ambushes him within 7, or the player uses it first, from in front of it or behind. See [wanderers](../systems/wanderers.md#wandering-noticing-and-chasing), from 1.0's code; what each start does in the battle is 2.5's.
- **Reference points** hold a facing vector at +0x14, which a teleporter arriving there turns the player to.
- **Whether an object is there** as its chunk loads is the core's `MapObjectPresence`, from the rules above. A herb, spice, gem or custom container needs both C and A, and hides its linked scene when it isn't there; an opened or destroyed chest, sack, crate or barrel swaps its linked scene's model for the second or third (`exploding_container_check`, from the decomp).
- **Dialogue objects** hold a staging chunk, which is none when its row is 0, and a base the script's reference point numbers count from, a multiple of 128. Using one doesn't write its B.

**A cut door:** the patioL2 door in Jundar's interiors K07 leads nowhere: the original has no arrival point for it in A01. It doesn't matter, since the room is cut content. K07 holds only the door and the reference point beside it, and nothing leads into it, as the user confirmed. The runtime needn't handle a missing arrival point beyond not crashing. It's map object 0 of `aidyn:map/0x1871` (`aidyn:voxel/0x1871/0`, open it in the editor), at (10.2, 4.2, 13.8) in the chunk beside the reference point MainDoorsPatio, and it leads to A01 (`aidyn:map/0x1890`) at point 0x800E.
- **Export.** `aidyn maps <rom> [<set>...]` writes each map set to `out/<version>/maps/`: `<set>.json` holds its chunks and every map object with its decoded fields, and `<set>.glb` its collision, a node per chunk at its origin. Each collision vertex carries its triangle's surface, role, flags and target as the attributes `_SURFACE`, `_ROLE`, `_FLAGS` and `_TARGET`: the target is the object a trigger triangle runs, by its index in the map, or a toggle's id, and 0 otherwise. All 17 files pass the glTF validator. The user checked them against the game on Sep 27, 2026: the layout, terrain, objects and enemy spawns are where they remember. The editor draws map sets over the base plugin with the runtime's code (see [inspector](../systems/inspector.md)).
