# Actors: Borg7 (roadmap 1B)

In this project *actor* means a Borg7: a scene with a state machine of animations. The decomp also uses `Actor` for a body moving through the world; see the glossary in CLAUDE.md.

- **Borg7 (203 actors)** is a 0xC-byte header (the root transform, the state count and the initial state), then 0xC-byte states (a Borg6, a u16 of flags, and the count and offset of the branches), then 4-byte branches (request, chance, flags, target state). Some files are padded to 8 bytes with leftover text. Every actor's root transform is 2 and every actor starts in state 0. All of an actor's animations animate one scene. There are 1,932 states and 9,227 branches, and actors use 1,923 of the 1,988 Borg6s.
- **Requests.** Each frame, the game asks each actor for an animation by number (`Borg7_SetAnimation`). The requests' names include 0 idle, 2 walk, 3 run, 7 hit, 9 dying and 25 sneak. The branches use 0–22, 25 and 255, which means any request. A state's flag 0x1 marks the initial state, in all but two actors (7613 and 7620). The game doesn't read it, and uses bit 0x2 of the same field at run time.
- **Branching** (`Borg7_TickAnimation`). When the scene clock reaches the animation's length, the game rolls 0–99. It walks the branches in order, and for each whose request is the current one or any, it subtracts the chance. It takes the first branch at which the roll drops below 1, so a chance of 10 after the roll is 11 in 100. With no branch taken, the animation restarts. When the request changes, branches with flag 0x1 that match it are rolled for at once, and the animation doesn't advance that tick. 3,755 branches interrupt like this.
- **The rolls** are `Range(0, 99)` (`Rng.RangeOn`, `0x80093384`, the game's generator on a stream it's given) on one of two streams of the actor animations' own, each shared by every actor: bodies' (`ActorStateMachine.Tick`, `0x80096570`, from `ProcessPlayers` once a body a frame) roll on the word at `0x800e69c0`, and map actors' and the pause menu's scroll's (`ActorStateMachine.Advance`, `0x800967a4`, which loops a frame's ticks) on `0x800e69c4`. Both are in `.bss`, start at 0 and are never seeded or saved, so a session's first roll is (100 × `0x3C6EF35F`) >> 32 = 23. The port gives bodies one stream too, `RandomStreams.Animation`, from 0 with every new or loaded game. The runtime steps map actors and the scroll by the rendered frame, so the order frames take them in would change a shared stream: each of those rolls on a stream of its own, from 0. The rolls are cosmetic; nothing in the rules reads them.
- **Brenna's actor (10723)** is a typical one. Idle (state 0) repeats 90% of the time and fidgets 10%. Walk or sneak starts a walk (1), which alternates two steps (2 and 3) and ends in a stop (4 or 5) when walking isn't requested. Run goes to state 6. Requests 5, 6, 12, 13 and 15 interrupt from 18 of her 25 states; the rest, including hit (7) and dying (9), interrupt only from idle and a few others.
- **Root motion.** The game draws the actor with transform 2's position zeroed (`Borg7_Render`), and moves the actor by how far that position moved each tick. It skips the tick a branch is taken or an animation restarts, and the two ticks after; and a body moves only while its request, or the request its state was entered under, isn't idle ([movement](../systems/movement.md)), so a stop's root returning to rest moves nothing. The walk steps are cut from one continuous walk, and skipping those ticks hides the jump back between steps. Brenna's walk comes to about 1.9 scene units a second.
- **In the port** the core plays an actor headlessly: `ActorMotion` (`Aidyn.Core.Actors`) holds its `ActorStateMachine`, with each state's length and the root's position at each tick read from its scene's asset by `ActorClips` (`Aidyn.Plugins.Assets`): each glTF animation's `length` extra, and the root node's per-tick samples, its translation plus its pivot turned and scaled by the sample's rotation and scale. A mod that replaces the scene's glTF replaces its timing and motion with it. An animation the scene lacks lasts a tick, and one that doesn't drive the root moves nothing. The first tick moves the body from where its initial state's root starts. The runtime's `ActorAnimator` poses the scene at the state and clock `ActorMotion` says.
- **Entities' actors** (`EntityModels`, from `gEntityExtras` and `dailougEnt_info_array`). Each entry is keyed by the record's position in the code's entity or dialogue entity list, plus 1. Both lists are in the same order as the DB tables. Keying by the record's ID instead would give Alaron Brenna's actor. All 221 entities and 32 of the 37 dialogue entities have an actor, a portrait, a height and a scale. Entities also have a collision radius and an unknown float. The import gives each entity and dialogue entity its `body`: actor, radius, scale and height (importer 20). Dialogue entities' radius is 0.55, which the code gives them all, and the five without an entry get the bat (`0x2D4A`) at scale and height 1, as the code does (`EntityDB::GetBorg7`). 104 actors are used this way, and the other 99 belong to scenery, spell effects, the pause menu and the like. The tables and the dialogue entity list are identical in all three ROMs.
- **Viewing.** The editor shows an actor's states and branches, with the interrupting ones highlighted; clicking a state plays it, and **Drive** runs the state machine for a chosen request with root motion, so Brenna's actor with walk requested starts, steps and stops (see [inspector](../systems/inspector.md)).
