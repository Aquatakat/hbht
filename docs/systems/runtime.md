# The runtime (M1–M4)

`src/HBHT.Game` is the Godot game. It references `HBHT.Plugins`, `HBHT.Core` and `HBHT.Views`, and not `HBHT.Rom`, so the build enforces ADR 0001. It draws with what it shares with the editor in `HBHT.Views` (ADR 0022); the rest of its views, and `Game`, which `Main.tscn` attaches by path, are its own. Import first ([importer](importer.md)), build with `dotnet build`, then run it with `tools/godot.ps1 --path src/HBHT.Game`. It reads the plugins from the data folder, so set `HBHT_DATA` for both if the import went elsewhere. It refuses a base plugin that's missing or was imported by another importer (`BasePlugin.Diagnose`), with the words the CLI and the editor use.

The runtime keeps its loops thin (ADR 0012): the core's `GameSession` plays the game, and the runtime draws what each tick leaves and carries out what it asks. Each system's doc says how its part is drawn; this one says how they fit together, and holds the debug keys and the command line.

## The data folder

The plugins, the saves and `settings.json` live in the data folder (`DataPaths.Root`, in `HBHT.Plugins`), which the game, the editor and the CLI resolve alike:

1. `HBHT_DATA` if it's set, which the tests, the tools and development use.
2. Else a portable install's `data` folder beside the executables, when the app's folder holds `portable.txt` (the Windows portable zip ships it, [releases](releases.md)) or already holds an import there (`data/plugins/aidyn.base`).
3. Else `HBHT` in the local application data folder: `%LOCALAPPDATA%\HBHT` on Windows, `~/.local/share/HBHT` on Linux, `~/Library/Application Support/HBHT` on macOS. The MSI install and the Linux tarball use it.

`HBHT.Plugins` doesn't know Godot, so the app folder is handed in: both Godot apps call `AppLauncher.UseAppFolder` (in `HBHT.Views`) from their main node's static constructor, before any field reads a path, and it calls `DataPaths.UseAppFolder` with the executable's folder only when exported (`OS.HasFeature("template")`) and not on macOS, whose app bundles have no portable mode. The CLI never calls it, nor do the apps run in development, so those go by steps 1 and 3. `DataPaths.Resolve` is the rule over its inputs (`DataPathsTests`).

## With no import

At startup, before anything loads, `Game` asks `BasePlugin.Diagnose` whether the base plugin is there and current. If it isn't, the game starts the editor with `--from-game 1` and quits, and the editor's import page imports and then offers **Play** ([editor](editor.md#the-import-page)). `AppLauncher.LaunchEditor` finds the editor beside the game: exported on Windows and Linux, `hbht-editor(.exe)` in the same folder; on macOS, `HBHT Editor.app` beside `HBHT.app`, through `open -n … --args`; in development, the same Godot binary with `--path` the repository's `src/HBHT.Editor`, found from `res://`. If it can't find or start it, or the run takes a screenshot, the game shows `Diagnose`'s words in its window, with a line saying to open the editor.

## How a tick runs

`GameSession.Start` builds the game where a `GameStart` says (a save's place, or a new game's arrival with the command line's overrides, `Game.StartingPlace`), and the runtime builds its player and camera views from `TrekLoop.Player` and `Camera`; the tests start their sessions the same way. Then `Game._PhysicsProcess` calls `GameSession.Tick` once per 60 Hz tick, which in order:

1. hands on the settings if they changed (`GameSession.Apply`), before anything steps ([ADR 0023](../adr/0023-the-core-is-handed-its-settings-each-tick.md));
2. counts the tick, in every mode: the time played and the game's ticker (`GameState.CountTick`, [saves](saves.md), [cameras](cameras.md#camera-objects-processvoxelcamera));
3. repeats the held directions (`StepStick`, [ui](ui.md#input));
4. steps the pause menu by the scroll actor's clock (`ScrollClock`); if it has closed, the session carries out its exit, gates the map again, and the tick returns `SessionStep.MenuClosed` without stepping a mode ([pause menu](pause-menu.md#opening-and-closing));
5. steps the mode that runs (`GameSession.Mode`, by precedence the title, a cinematic, the credits, the pause menu, a backdrop's page, a map object's popup, a conversation, a cut-scene, a battle, else trek): trek's `TrekLoop` ([map objects](map-objects.md), [wanderers](wanderers.md)), a cut-scene's `CutScene.Tick` ([scripts](scripts.md#cut-scenes)), a battle's `Battle.Tick` ([combat](combat.md#the-port)), a cinematic or the credits ([cinematics](cinematics.md), [ui](ui.md#the-credits)), or the title's cards and fly-throughs ([ui](ui.md#the-title-screen));
6. fades a backdrop's page (`Trek.StepBackdrop`, [ui](ui.md#books-and-the-help-menu)) and twinkles the stars (`Sky.StepTwinkle`, [rendering](rendering.md#the-skys-objects)).

The tick returns a `SessionStep`, and the runtime draws the mode it names, holding the world's views still by `GameSession.Mode` rather than working it out. Everything else the core asks comes through its hosts, which `Game` is:

- `ITransitionHost.Transition`: every ending of a mode, the menu or a script, in order, decided in the core ([below](#transitions)).
- `ITrekHost`: a teleporter's arrival, a conversation's page, a wanderer's root motion, a scene object's animation, change or path light put out, and a chunk whose objects came or went as the map was gated again (`Regated`, which rebuilds its scenery).
- `ICombatHost`: a battle's one-offs as cues ([combat](combat.md#what-a-battle-tells-its-host)).
- `IPauseMenuHost`: the menu's sounds and the scroll's steps (`Cue`), a save with the menu's snapshot (`Save`) and the screen the window is on (`Screen`). `PauseMenuView` only binds the tabs' views to each opening's models and lays them out ([pause menu](pause-menu.md)).

A press is the session's too: the runtime turns Godot's event into a `MenuAction` (`MenuStick`), and `GameSession.Press` sends it to the mode that runs ([ui](ui.md#input)). `Game._Process` draws between ticks, and Godot's physics interpolation smooths bodies.

## Transitions

`Transition` is where the game goes as a mode, the menu or a script ends (ADR 0019); the core has carried out its rules, and `Game` shows it:

- **The menu's openings** (a shop, training, a loot window, Start's menu, a battle's pause, the post-battle windows, the menu reopened after a cinematic or the credits) open `PauseMenuView` on the menu the session has already opened.
- **A cut-scene** shows its stage and its actors (`StartCutScene`) and frees them (`EndCutScene`); **a battle** shows its arena (`StartedBattle`) and frees it (`EndBattle`); `ResumeTrek` shows trek's world again. A `StartBattle` reaches the runtime only where trek didn't cue it, so it's only said.
- **The title** (`ShowTitle`, `StartTitleScenery`, `EndTitleScenery`, `EndTitle`): `TitleLayer` draws its cards, logo and menu, and `Game.Title.cs` its fly-throughs' scenery and camera ([ui](ui.md#the-title-screen)). A plain launch shows it over a new game's session (`Game.Start`), and New Game ends it into the same session's game.
- **The credits** and **a cinematic** start and end their layers (`CreditsLayer`, `CinematicLayer`; [ui](ui.md#the-credits), [cinematics](cinematics.md)).
- **Loading a save** (`LoadGame`, from the System tab or the title) reloads the Godot scene from the save, keeping the plugins loaded ([saves](saves.md), [pause menu](pause-menu.md#saving-and-loading)). **The game over** and the ending's credits (`GameOver`) reload it on the title over a new game, its intro cards first (`Game.GameOver`), as the original restarts at it; **Return to Title** (`ToTitle`) does the same at the logo (`Game.ToTitle`). **Quit** ends the program (`Game.Quit`), saving the window's size first if that was waiting.
- `Say` shows a line on screen; `Camp` and `Rest` are only logged.

## What it draws

- **The world** a mode plays in is a `ZoneEngine` (the original's `InitZoneEngine` and `HandleZoneEngineFrame`): the chunks with their collision, sounds and lights, the music, the weather and the sky. Trek has one, a cut-scene's stage is another made from it (`ZoneEngine.Stage`, [scripts](scripts.md#the-world-it-plays-in)), and a battle's arena is a stage on the Battle arenas. `ChunkStreamerView` draws its chunks' scenes, scene objects and actors ([rendering](rendering.md)); `SkyView` pushes its sky to the shaders, with `SkyBackdropView` and `LensFlareView` ([rendering](rendering.md#the-skys-colours)); each frame's lights start with `ZoneEngine.BeginLightFrame` ([rendering](rendering.md#point-lights)).
- **Bodies.** The player is `Game`'s (`Player`); every other body is a `BodyView`: `WandererView`, `CutSceneActorView` (with the item in its hand) and `CombatantView` ([combat](combat.md#the-port)). A `BodyView` holds the actor at its scale, faded and lit, with its shadow (`ShadowDecal`, [movement](movement.md#shadows)); the core's `ActorMotion` times it and `ActorAnimator` poses it ([actors](../formats/actors.md)).
- **Screens.** `HudView` and the battle screen's views, `PauseMenuView`, `TrekPopupView`, `BackdropLayer`, `CinematicLayer`, `CreditsLayer` and `TitleLayer` draw what the core's models hold ([ui](ui.md), [pause menu](pause-menu.md), [cinematics](cinematics.md)).
- **Audio.** `AudioOutput` plays the core's `GameAudio` on its own thread through a Godot generator stream ([audio](audio.md)).
- **Settings** ([ADR 0013](../adr/0013-settings-in-the-options-menu.md), [pause menu](pause-menu.md#options)) are kept in `settings.json`, with the command line's lying over them (`LaunchSettings`). `Game.ApplySettings` makes the session's `SessionSettings` again as they change, and carries out what's only drawn (the window, v-sync and the frame rate limit, anti-aliasing, the 3D resolution, Draw Distance and Object Distance, model detail, the UI's lines and filter).
- **Quick save.** F8 saves to `quick.json` in the saves folder, with where the player stands (`GameSession.NotePlace`).

## Traps

- **Cadence** ([ADR 0017](../adr/0017-the-core-steps-every-tick.md)): where the original acts once a frame, the port matches an idealized 30 fps, a `delta` of 2 (`Cadence`), the user's choice; the console runs at 15–25 fps. Code that acts once a frame counts its ticks with `FrameGate`.
- **Nothing in the core reads `Settings`** but the options menu, which changes them. The rules play by the `SessionSettings` each tick hands in; headless tests hand `SessionSettings.Original`.
- **Trek's chunks stream only while its world is built** (`GameSession.StreamsTrek`). `Game._Process` moves the 3×3 with the player or the free camera, under the pause menu too, but not under a stage, an arena or the post-battle windows, where loading trek's chunks would play their sounds. Then it brings the scenery round the 3×3 (`SceneryRing`, [rendering](rendering.md#draw-distance)), in trek alone: the chunks the 3×3's chunks show, and under Draw Distance's Extended the 5×5.
- **A loaded chunk is known by its `ChunkKey`**: map set, row and column. Collision, drawn surfaces, map objects (`LoadedMap.Key`), trigger triangles, an arena's grid and a stage's rain all name it, so two map sets' I08 are never taken for each other.
- **Gating** happens as a chunk loads, and again where the original reloads the map ([scripts](scripts.md#its-boundary)): the pause menu's closing regates the loaded chunks (`TrekLoop.Regate`), and `ITrekHost.Regated` rebuilds the scenery of each whose objects came or went.
- **A window being resized must keep drawing frames.** Godot 4.7 remakes a view's render buffers at each step of the window's size and frees the old ones only as frames go by, and on Windows a quick drag of the window's edge starves the timer it draws frames from. The steps' buffers piled up, hundreds of MB each at 8× MSAA, until the card ran out of memory (`VkResult -2`) and every frame after failed in a spew of render errors; a bare Godot project does the same. So while the window's size changes in a burst, `Game.WindowChanged` draws the 3D views without MSAA and at Godot's smallest 3D scale, till the size has been still 0.3 s, and draws a frame, unshown, every four steps without one (`RenderingServer.ForceDraw`). A view sized by code is sized once a frame, as `PauseScrollView` is.

## Loading chunks

[ADR 0025](../adr/0025-chunks-load-off-the-main-thread.md). Crossing into another chunk loads the chunks that come into the 3×3; the original stalls as it does, and the port spreads the work.

- **On the main thread, as the chunk loads** (`ChunkStreamer.Update`, from `Game._Process` on a crossing and from trek's tick on a teleport or a reload): its collision, its map objects activated by the flags (`LoadedMap.Activate`), its drawn surfaces, its sounds, lights and wanderers, and each wanderer's view with the motion the core steps its body by (`BodyView`), which rolls on the game's animation stream. So is the scenery of a chunk within three quarters of a chunk of where the 3×3 was loaded about (`ChunkStreamerView.NearBuild`), the chunk the player is in among them, and a wanderer's body within 40 of it (`NearBody`), and every view of a cut-scene's stage and a battle's arena.
- **On the builder's thread** (`ChunkBuilder`, one job at a time): the scenery of the other chunks the 3×3 loads, 100 away on a crossing, and of every chunk of the ring of scenery round it, built outside the tree from the objects as they stood when the chunk loaded, and the rest of the wanderers' bodies. Then, while nothing waits to be built, it reads ahead what the next crossing could load: for the chunks two from the centre, their drawn surfaces' triangles (`ChunkStreamer.Prepare`), their scenes and objects (`Models.Warm`) and their monster parties' actors, and under the ring, the scenes of those three from it. A new centre drops what was still to read.
- **Back on the main thread, a frame or a few later**: `ChunkStreamerView.Flush` adds one built chunk a frame to the tree, leaving out an object put out since its build began, and each wanderer's body as it's built (`BodyView.TakeBuilt`), whose emitters start then. A chunk going from the 3×3 into the ring or back keeps its old scenery drawn until its new scenery is added (`ChunkStreamerView.Settle`), so nothing goes missing as it changes hands.

Traps:

- **The main thread must never wait on the builder.** Godot's renderer serves another thread's calls on the main thread between frames, so the builder can be waiting on the main thread. `Models` parses its own copy of an asset the builder is parsing rather than wait, `N64Material` compiles a shader outside its cache's lock, and `ChunkBuilder.Dispose` serves the renderer while it waits for the job under way. A lock the main thread can take, held across a call into the renderer, deadlocks the game.
- **Calls into the renderer from the main thread wait while the builder makes resources**, a few milliseconds each. Something the main thread calls every frame, such as the follow camera's far plane, should be set only as it changes.

## Controls

Every control can be rebound on the options' Controls page, which lists them by situation with their defaults ([pause menu](pause-menu.md#controls), [ADR 0026](../adr/0026-controls-are-bound-by-situation.md)); how they steer the camera is in [cameras](cameras.md#the-follow-camera-cameramode0), and aiming in a battle in [combat](combat.md).

- **How input is read.** The bindings (`Settings.Controls`) become Godot's input actions as the game starts and whenever they change (`InputBindings.Apply`, from `Game.AddInputs`): one action per button, named for its control (`menu_accept`, `battle_spells`), and four per direction, its sources' directions: `move_*` for Move's own sources, `steer_*` for those Move and Camera share, `look_*` for Camera's own, and `menu_*` and `target_*` for the menus' (a conversation's too) and a battle's. `MenuStick` translates an event by the controls of the situation the game is in (`Situations.Of(GameMode)`), and `Game.ReadInput` (in `Game.Input.cs`) reads the stick, the camera and Sneak for trek and a battle's turn. Nothing reads a key directly.
- **The mouse.** With the mouse on the Camera row it always turns the camera, captured in trek and a battle and let go in the menus, a conversation and the free camera (`Game.CaptureMouse`).
- **The debug keys aren't the player's to bind** (`Game.AddInputs`), and a control can't take F3 or F5–F11. F toggles a free camera (Space and C for up and down, Shift for faster). F3 toggles the debug overlay (`Game.Debug.cs`): in trek the chunk, position, surface, speed, request, pace, movement, camera, sounds, particles, rain and what a cut-scene waits for; in a battle its state, turns, field and combatants. F5 toggles the pace, F6 the sky's placement and F7 the UI screen's height. In a battle, F9 moves the radar between the log box and the screen's corner, and F10 routs the enemies and F11 fells the party, so that the next turn's change (Z) wins or loses it (`Battle.Rout`, `Collapse`).
- **Fast-forward:** holding either thumbstick down (L3 or R3) raises the tick rate from 60 to 240 a second, as far as the machine keeps up (`Game.SetTickRate`). The pause menu stays at 60.
- **Holding Cancel (B, Backspace) for two seconds in a battle wins it** on the next turn the player plays, as F10 and Z would (`Battle.ForceWin`, `Game.HoldToWin`). The seconds are the clock's, so fast-forward doesn't shorten them. Not in the Shadow's battles, which end in the merge or its vanishing, never a win.
- **Release builds have none of these** (`Game.Debugging`, `OS.IsDebugBuild()`, false in the release packages): the debug keys' actions exist with nothing bound to them, so `--press battle_rout` still works, the overlay starts hidden, fast-forward has no buttons and holding B doesn't win. A run under the Godot editor's binary is a debug build, with all of them and the overlay showing.

## The command line

After `--`: `tools/godot.ps1 --path src/HBHT.Game -- --chunk I08 --at 16,62 --yaw 0 --pitch -15 --distance 5 --hold move_forward,4 --screenshot <absolute path>.png` starts somewhere, holds an input, saves the window and quits. The run gives up after a minute; launch it with a process you can kill, not blocking on it. `LaunchOptions` reads the options (on top of `CommandLine`, the parser and screenshot the editor shares), `Game.Start` builds the game in named steps from them, and `Game.Debug.cs` carries out the ones that drive it (`RunLaunchActions`). The launch options run once a run: a load or a game over that starts the scene again doesn't play them again.

- **Where:** `--set n`, `--chunk`, `--at x,z` (by default where a new game starts), `--yaw`, `--pitch`, `--distance`; `--fly x,y,z` starts with the free camera, which scene objects' distances are then measured from; `--camera outdoor|interior` starts in either mode (by default the start chooses as a door into its chunk would). Gwernia's open ground is around (30–80, 30–80) in M07, for example `--chunk M07 --at 40,55`; elsewhere in M07 there's no ground, and he falls and is lifted again and again, as in the original ([movement](movement.md)).
- **The game:** `--save <path>` starts from a save, where it stands unless `--chunk` or `--at` say otherwise. `--flags 5,50` sets plain flags before anything loads. A plain launch shows the title, its intro cards first, over a new game ([ui](ui.md#the-title-screen)), and its New Game plays the opening cinematic, then script 866 on its stage, then trek in I08 (`GameSession.StartNewGame`, [cinematics](cinematics.md#what-starts-them)). A save with no place starts as New Game does, without the title (`GameState.StartsAsNewGame`, [saves](saves.md#the-format)). Any option that says where to start or drives the run (`--save`, `--set`, `--chunk`, `--at`, `--flags`, `--fly`, `--hold`, `--press`, `--menu`, `--cutscene`, `--cinematic`, `--battle`, `--screenshot`) skips the title and the opening and starts in trek, where the opening's cut-scene still starts from its object unless `--flags 5,11` is added; `--opening on` or `off` says which outright, and `--opening on` plays it without the title. `--title cards` shows the title with its cards, `--title logo` without them, and `--title off` not at all; options are pairs, so `--title` takes one of those. `--time <hours>` sets the time of day.
- **Input:** `--hold` holds actions for so many seconds, several joined with `+`, as in `move_forward+walk,4`. `--press pause,menu_member_left,menu_right` presses actions in turn, a fifth of a second apart, as input events, which `--hold` doesn't make; the screenshot waits for them. The names are the controls' actions, read by the situation the game is in, so the menus take `menu_accept` and `menu_down`, a battle `battle_attack` and `target_left`, a conversation the menus' `menu_accept` and `menu_down` too, and trek `pause` and `use`. Among them, `wait:2` waits two seconds more; `battle_target:1.3` holds the action that long, pressed and let go as events, so combat's held menus hear both; and a `+` after it (`battle_spells:1.6+`) sends the next presses while it's held. A binding's name, `Key:P`, `Joy:Y` or `Axis:LeftX-`, presses that input itself, as the Controls page's prompt hears it. `battle_rout` routs a battle's enemies, as F10 does.
- **Menus and scenes:** `--menu 1` opens the pause menu, `--menu system`, `party` or `world` opens it on that tab, `--menu loot` opens an empty loot window, and `--menu train:aidyn:entity/0x0213` opens training with that entity as the trainer. `--cutscene aidyn:dialogue/0x0365` plays a cut-scene at once (the goblin ambush). `--battle aidyn:voxel/0x0F6B/3[,<arena>][,ambush]` starts a battle with that monster party where the player stands, in the arena given or the one the terrain chooses. `--radar box` puts the battle screen's radar in the log box (F9 swaps it). `--cinematic <n>` plays a cinematic, 0 to 3, without the menu after, and what follows it in the story (the opening's script, Roog's True Name, the ending's credits and the game's end); `--cinematic 0,5,300` starts at shot 5's time 300, and `--cinematic 0,5,300,hold` stands still there.
- **Weather:** `--weather rain|snow|fog|clear[,intensity[,fog]]` sets it at once, already set in and with the rain sky up (rain and snow default to 0.5 with fog 0.2 and a storm as hard as the rain; fog to 0.5). Rain and snow take a few seconds to fall into view from a standing start, so hold something harmless, such as `--hold walk,8`, before the screenshot.
- **Settings for the run:** `--ui-lines <n>`, `--sky original|projected`, `--pace`, `--movement original|smoother` (`modern` too), `--draw-distance original|extended`, `--object-distance <scale>`, `--detail nearest`, `--precipitation <scale>` (up to 8) and `--spell-auras each` lie over the player's settings for the run (`LaunchSettings`), and are never written to `settings.json`. Each holds until the player changes that setting, in the options menu or with F5, F6 or F7; `--pace` gives way to the Pace setting. `--lights off` lights bodies and actors by the sky alone ([rendering](rendering.md#point-lights)), and `--spell-fx off` drops spells' visuals, sky dimming and body tints ([combat](combat-actions.md#what-spells-look-like)), as baselines.
- **Screenshots.** The path must be absolute, or Godot saves it relative to the project. `--ui-screenshot <png>` saves trek's UI screen with it, in its own pixels and with its alpha, for measuring the HUD and the battle screen against the user's captures. `--screenshot <png> --frames <n>` saves the next n frames as they're rendered, in real time, as `<png stem>-000.png` on, kept in memory until the last: for what only shows above 60 fps, between ticks. To see something tick by tick, Godot's movie writer saves every frame at a fixed 60 a second: `tools/godot.ps1 --path src/HBHT.Game --write-movie <absolute dir>/f.png --quit-after <frames> -- --menu party`. It records at the project's window size, 1280 × 960; Godot's `--resolution` doesn't change it, and `--ui-lines 960` puts a window pixel to each of the UI screen's.
