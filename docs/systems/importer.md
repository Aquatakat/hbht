# The importer and the base plugin (M1)

`aidyn import <rom>` turns a ROM into `aidyn.base`, the plugin the runtime loads (ADR 0001). It goes to `plugins/aidyn.base` in the data folder: `AIDYN_DATA` if set, else `%LOCALAPPDATA%\Aidyn`. `--out` puts it elsewhere. It refuses the debug ROM (ADR 0007).

- **Layout.** `plugin.json` records the importer version (`BasePlugin.ImporterVersion`) and the ROM's SHA-1, so the runtime can tell when to re-import (`BasePlugin.Diagnose`, which the runtime, the CLI and the editor all go by). Installed plugins load after the base in dependency order (`PluginSet.LoadOrder`: `dependencies` first, `loadAfter` when that plugin is present, ties by ID; a cycle or a folder not named for its plugin's ID is an error). `records/` holds the record files below; the loader reads every JSON file under `records/`, whatever the layout (ADR 0005), so the split is only for reading and diffing. Maps are a file per map set (`maps/Overworld.json` and so on), since each map is in one set; the runtime still loads every map record at start. `assets/aidyn/<type>/<key>.glb` holds every scene (`aidyn:scene/0xHHHH`, the same glTF as `aidyn scenes`) and every chunk's collision (`aidyn:map/0xHHHH`, in the chunk's own coordinates); every texture is a PNG (`aidyn:texture/0xHHHH`, full size only) and every UI image one too (`aidyn:image/0xHHHH`, which includes the sky gradients). Scenes carry their own textures; the texture records are for what the engine draws with a texture alone, such as bodies' shadows and particles. A mod replaces an asset by putting a file at the same path in its own `assets/`. The core reads some assets itself, headlessly: chunks' collision (`CollisionMesh`), scenes' triangles (`SceneMesh`), actors' timing and root motion from their scenes' animations (`ActorClips`), and images' sizes from their PNGs' headers (`PluginSet.ImageSize`), which the sky's sprites and the minimap are placed by.
- **Scenes have locator nodes** (`locator <i>`, under their transform), for what the game attaches at run time. Alaron's actor record names his head scene and its locator.
- **Records.**
  - Map sets are `aidyn:mapset/<n>`, numbered as the original's `EnumMapDatA`, with the cell size and chunk list. They carry the places the code puts the player by number (`spawns`, importer 52). A map (`aidyn:map/0xHHHH`, a Borg9) holds its map objects of every type but the code objects, keyed by index (see [maps](../formats/maps.md#map-objects-in-the-base-plugin-06)). Scene objects' models name a scene or an actor, and they keep the original's rotation angles.
  - Actors (`aidyn:actor/0xHHHH`) hold their scene and state machine. Nine are marked `alwaysAnimated`, the ones combat keeps animating far from the camera. Terrains (`aidyn:terrain/<n>`, 0–27) name their sky gradient and whether it's drawn (see [rendering](rendering.md)), and the Battle arenas their battles take (see [combat](combat.md)). The combat record (`aidyn:combat/0`, `combat.json`, `CombatImporter`) holds who fights with the party, who never fights, the Skeleton and the flee rules, who never moves (importer 40), and the weapons that fly (importer 42): `missiles`, the two lists of weapon DB positions read from the code segment per version (`CodeTable.BowKindWeapons`, `ThrownKindWeapons`), each with its scene (a bow's arrow, Borg5 `0x348F`, else the weapon's own model), its muzzle speed and its turn as facts checked against the weapon's name, and `closeRange`, Spikes. Its `text` (importer 45, `CombatImporter.ReadText`) is the combat menus' and Sense Aura's words, which 1.0 keeps as C strings in its code segment (`CodeTable.CombatLayOnHands` to `AuraResistantBelow`, each with a range per version, the strings read as `MenuTables` reads its messages): the skill list's rows, the empty lists' lines, the popup's lines as printf formats, the 2.0 that a resistance's multiplier is compared with, and the 17 element names, which are `String/Common`'s lines 241 to 257 in all three ROMs ([hardcoded content](../hardcoded-content.md)). Spells and potions carry their effects (importer 41, `MagicImporter`, ADR 0020): the ROM keeps none of it as data, since the original's code switches on a spell's kind, so each spell's effects, duration, resist rule, target filter and AI value are facts checked against 1.0's machine code, and the importer fails on a spell without one, a fact without a spell, or a name or entity place that differs. The magic record (`aidyn:magic/0`, `magic.json`) holds casting's numbers, with its float tables read from the code segment (`CodeTable.CastingFactors`, `CastingFactors`). Spells and potions also carry what they show in a battle (importer 47, `SpellVisualTables`, `MagicImporter.WithVisuals` and `WithPotionVisuals`): `visuals` holds an actor at the caster and one at the target (a potion has one, at whoever drinks it), whether the target's stands at the head, a lasting aura scene and the memory the actors ask for, read from 1.0's five spell-visual `switch` functions by decoding their jump tables and case blocks (`CodeTable.SpellVisualCasterActor` to `SpellVisualPotionAura`, `SpellVisualJumpTables`, per version), with every Borg checked as an actor or a scene; the magic record's `refused` and `resisted` are the two actors the immediates `addiu s3, zero, imm` name (`CodeTable.SpellVisualRefusedResisted`).
  - `sky.json` is the one sky record (`aidyn:sky/0`): the sun, moon and stars, the clouds and the lens flare's pieces, read from the code segment, with the UI images they are drawn with. The images are literals in engine code, so the importer carries them as facts (`Skies`) and refuses a ROM where one isn't a UI image.
  - `sequences.json` holds every Borg12 as `aidyn:sequence/0xHHHH`, whose events are the asset `sequence/0xHHHH.dcm`, and every Borg11 is `sample/0xHHHH.wav` ([audio](../formats/audio.md#in-the-base-plugin)). `sounds.json` is the one sounds record (`aidyn:sounds/0`): what the menus, scripts, containers and weather play, and the bodies' footsteps by kind; the map sets' music is on their records, and bodies' audio keys on the entities' ([audio](audio.md#whats-ported)).
  - `emitters.json` holds each scene's particle emitters as `aidyn:emitters/0xHHHH`, keyed by the scene, with each emitter's texture slot looked up in the engine's particle list (`partTextInds`) to a texture record ([particles](../formats/particles.md)). `cinematics.json` holds the four cinematics (`aidyn:cinematic/0`–`3`): each shot's animation, music and near and far planes, and the flag set at the end. `credits.json` holds the credits (`aidyn:credits/0`). `title.json` holds the title screen's six fly-throughs (`aidyn:title/0`, importer 52; see [hardcoded content](../hardcoded-content.md)).
  - The fonts (`aidyn:font/<n>`) and the string tables (`aidyn:strings/<n>`) are in `fonts.json` and `strings.json`, and entities and dialogue entities carry their portraits (see [text](../formats/text.md)). The flags, journal and state flags, the scripts (`dialogue.json`) and the DB tables' records (`entities.json`, `items.json`, `weapons.json`, `armor.json`, `spells.json`, `skills.json`, `shops.json`, `loot.json`, `recipes.json`, `inventory.json`, `minimaps.json`, `worldmap.json`, `weather.json`, `camping.json`, `newgame.json` (`aidyn:newgame/0`, where a new game starts and who leads, [runtime](runtime.md)) and the rest of `records/`) are there too; each is described with its system.
- **Code.** `BaseImporter.Import` stages the plugin in a sibling folder and moves it into place when it's done. An `ImportContext` holds what the families share: the ROM, its Borg archive and DB, each code-segment table read once on first use (`EngineTables`, `BodySoundTables`, `AudioTables` and the rest), and the writers for records and assets. An importer per family builds its records from it: `WorldImporter` (map sets, terrains, weather, the World tab's map, camping, the sky), `FlagImporter` (flags, journal, state flags), `CharacterImporter` (dialogue entities' names, entities, spells, stats, skills, progression), `ItemImporter` (weapons, armor, items, loot, shops, recipes, inventory), `TextImporter` (strings, fonts), `DialogueImporter` (Borg13 scripts), `CinematicImporter` (the four cinematics, the credits), `MapImporter` (minimaps, maps and their collision), `GraphicsImporter` (actors, scenes and their emitters, textures, UI images) and `AudioImporter` (the sounds record, sequences, samples). `BodySoundImporter` and `MinimapImporter` build the sounds and minimap records the others write. A reader of the ROM's bytes uses `Be` (big-endian fields, tables as arrays, lists up to a terminator, a Borg's bounds-checked slice) and `RomImage.Table` for a table's range in the version's layout.
- **Deterministic.** Two imports are byte-identical, which a test checks. JSON is indented, with vectors and colours on one line, so two imports diff cleanly.
- **Merging** follows ADR 0005 (`MergePatch`): a patch merges field by field (RFC 7386: a scalar replaces, an object merges, `null` removes), except that a **keyed list** merges element by element. A list is keyed by the `[KeyedList]` attribute on its property in the record type, which names the element's key fields; `RecordSchema` reads it, and the rest of the merge's knowledge of the types, from the serializer's own metadata, so the merge and the record types can't drift. Each element of a patch's list names its element by the key: one the record has merges into it like an object, one it lacks is added at the end, and `{ "index": 12, "$remove": true }` removes it. The keyed lists are the ones whose elements something else names by the key: a map's `objects` by `index` (the voxel ID's last segment), a script's `nodes` by `index` (what its links name), a map set's `chunks` by `row` and `column` and its `spawns` by `portal`, an entity's `spells` by `spell` and `resistances` by `element`, a shop's `stock` and a recipe's `ingredients` by `item`, the combat record's `missiles` by `weapon`, `bosses` by `entity`, `fleeByEncounter` and `encounters` by `flag` and `flaskDanger` by `item`, and the world map's `pieces` by `flag` and `towns` by `image`. A list whose elements' identity is their position (an actor's states, the sounds record's kinds, a progression's levels, a string table's lines, a cinematic's shots) is replaced whole, since removing one would renumber the rest; so is one whose elements repeat (a loot table's drops, a minimap's sections and rules), and any other. The base's keyed lists have unique keys (`KeyedListTests`). Removing a script's node is refused by the script VM, which needs node *i* at position *i*; inserting and removing nodes is the finer list operation ADR 0005 leaves to Phase 5. A record object's `$schema` is ignored, for editors.
- **The conflict report** (`PluginSet.Conflicts`, `aidyn conflicts`, and a count in the editor's status line) lists every field that more than one plugin *patched*, by *path*: a top-level field (`damage`), or through keyed lists an element added or removed (`objects[12]`) or a field in one (`objects[12].position`, `chunks[9,8].music`). A field's merge into a nested object counts as the top-level field. The record's definer doesn't count: the base sets every field of its records, and one mod patching a field is a patch, not a conflict. `PluginSet.Setters(id, path)` gives everyone who set a path or one enclosing it, the definer first, which the editor shows per field; `Patchers(id)` gives who patched the record at all.
- **Validation** (`PluginSet.Validate`). Reads keep the lenient options (`PluginJson.Options`: a view such as `DbRecord` reads part of a record, and a save skips what it doesn't know), so a typo'd field in a patch would merge and be ignored, a typo'd `type` would read as a base map object, and a malformed record would throw on first read, mid-game. So `Validate` reads every record of a type with a class (`RecordTypes.ClassOf`) once with `PluginJson.Strict`, which refuses a field the type lacks, a `type` discriminator no kind has, a null the type doesn't allow and a missing field with no default (a constructor parameter that's neither nullable, defaulted nor dropped by a `JsonIgnore` condition), and also refuses a keyed list with two elements of one key; what reads is kept as the typed record. The report (`ValidationReport`) names each problem's record, its setter path and **the plugin that last set that path**, found from the serializer's path through the setters, so a typo in a mod's patch of one map object is blamed on that mod at `objects[12].radious`, not on the base. The base's 8,900 records take under a second. **Every problem is an error, in any plugin**: an unknown field or kind in a mod is never what its author meant, and a warning would let the game play around it, which is the gap this closes; a mod for a newer engine gets an honest refusal rather than a half-applied mod. `LoadInstalledChecked`, which the runtime and the CLI load by, throws the report as it throws the import's staleness message, so the game and `aidyn` commands show it and stop; the editor (`RecordBrowser`) shows it in its status and loads the records anyway, since it's where they're fixed. A record object's `$schema` is stripped before validation.
- **JSON Schema** (`RecordSchema.JsonSchema`, `aidyn schema <dir>`). A draft 2020-12 schema per record type is exported from the strict options with `JsonSchemaExporter`, so a schema refuses what validation refuses: `<type>.schema.json` for a record (`id`, the fields without a default required, no other fields) and `<type>.patch.schema.json` for a patch to one (`patch` required, every field optional and nullable all the way down, since a nested object patch is partial too, and `$remove` on a keyed list's elements). IDs are strings matching `RecordSchema.IdPattern`, vectors and colours arrays of fixed length, which the custom converters would otherwise export as "anything". `SchemaRoundTripTests` validates a real record of every type against its schema with JsonSchema.Net (a test-only dependency) and checks it reads strictly and writes back the same JSON; `SchemaTests` checks the shape.
- **Reading records.** `PluginSet.Get`, `TryGet` and `All` read the merged JSON as a record type once and keep it: every later call for that record and type returns the same object, and `All` holds those same objects, in the order of their IDs' spelling. The records are immutable, and nothing changes the merged JSON once the set has loaded (`GetJson` hands out the set's own, to read), so the cache never goes stale; it's safe from the audio thread. A record read as two types, as `DbRecord` reads part of an entity's, is one object per type. A type there's only one of (`aidyn:camping/0`, the sky, the sounds, the credits and the like) is read with `Singleton` or `TrySingleton`, which take its `aidyn:<type>/0`; a mod patches it rather than adding another.
