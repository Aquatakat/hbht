# The flag engine (roadmap 2.1)

`HBHT.Core.Flags`: `FlagNetwork` (every flag's value and the derived flags' evaluation) and `StateFlags` (what the engine writes into flags). The flag table's format and what reads and sets each flag are in [quests](../formats/quests.md). They port the original's `ProcessGameStates` and the getters and setters in `gamestatelib.cpp` and `gameStateFunnel.cpp`, from 1.0's machine code.

## The records

The importer writes three record types:

- **Flags** (`aidyn:flag/n`): every `GameStateFunnel` entry from 0 to 5555. A plain flag that starts a new game set has `initial` (only flag 1 does). A derived flag has a formula: its kind, operation, operand and inputs, as record IDs. A flag may have a label ([below](#labels)). A flag that lists a journal entry names it (`journal`).
- **Journal entries** (`aidyn:journal/n`): the text. The flag that names an entry lists it: the journal shows it while the flag is set, and adds it when the flag turns on. Every entry's flag is plain but entry 32's, derived 5017. A mod adds an entry with its text and a flag that names it. **Eleven entries never show:** nothing in the data or the engine sets their flags (142, 223, 274, 287, 297, 362, 390, 511, 512, 513 and 542, entries 12, 21, 28, 33, 36, 41, 45, 59, 60, 61 and 66), and none is set in any story checkpoint, the one before the final encounter among them. They read as the story's own (the voyage to Cradawgh's Isle, the Horn under the Barrow), so they're entries the game wrote and never wired up. The port keeps that.
- **The original's journal triggers aren't imported.** 1.0 adds an entry through a derived flag of its own, 5556 + *i*, which is `count(entry i's flag) > 0` and nothing else; nothing else reads those 71 (no formula, script, map object or engine code names them, and saves keep only the plain flags below 5001). The importer checks each is that formula over its entry's flag, leaves them out, and puts `journal` on the entry's own flag; the network does what their writes did ([below](#the-network)).
- **The state flags** (`aidyn:stateflags/0`): which flags the engine writes its own state into, and the new journal entry flag (3617). It's a layer 3 feature (ADR 0008), so a mod can move them. It also names the random skill checks' flag (3717), which only the dialogue's skill check reads (`Dialogue.Condition`, `0x8004f680`, case 0x19): nothing in 1.0's or the debug build's code writes it (every literal flag passed to `FlagNetwork.Set`, `0x8001fda8`, is another), so it's clear in every game unless a mod or a save sets it.

## Labels

The ROM names no flags: a `GameStateFunnel` entry is a kind, a starting value and a formula, and the debug build's strings name none either. Every label is ours, and the importer writes them (`FlagLabels`):

- **From the content tables in the code segment**, with a name the ROM gives: the party's members, the key items, the bosses, the cinematics' titles and the world map's regions; and from `EngineFlags`, the flags engine code names.
- **The rest from `FlagNames.tsv`** (`HBHT.Rom.Quests`, embedded), by number, written by hand. A flag no table names that's unused or play never sets ([below](#which-flags-are-used)) has none. The import fails if the file names a flag a table names. The flag table is the same in 1.0, 1.1 and the debug build, so one file serves each.
  - **The map objects' flags** were named from the object that writes them and the place of its chunk: "Opened the chest in the desert", "Talked to Cadme approaching Erromon or in Oisin forest", "Found the secret door in Shamsuk's Tower C11 (object 3)". The places are in `ChunkPlaces.tsv` beside it, each chunk's as it follows a verb ("in Gwernia", "outside Terminor", "in the Gwernia Castle throne room"), drafted from each chunk's doors, people, signs and talk and then corrected by the user; the map set's name is no guide (JundarInteriors is Talewok's). Where two flags' names would match, the chunk's cell is added to a place several chunks share ("in the desert P26"), and where they still would, the objects' indexes. A container sets its opened and Used flags as one act, so where they differ the two share a name.
  - **The others** were drafted from the scripts that set and read them and the chunks around them, then restyled after the user's own edits to the drafts.

`QuestIndexRealDataTests.EveryUsedFlagHasALabelOfItsOwn` holds the file to that: every flag that's used and can change in play has a label, no other has one but the tables', and two flags share one only where the same records write both, or two derived flags have one formula.

A label is the simplest phrase that tells a flag apart from every other:

- **An event in the past tense, a state in the present.** A flag the game sets once and never clears is named for what happened: "Defeated Kitarak", "Awoke in Oriana's hut", "Revealed world map region 1". One that can clear again holds a state: "Brenna is in the party", "Has Rabisat's Asp", "Checking for camp dialogue".
- **For what sets it.** A flag nothing in the data sets is named for what its readers see ("The lighthouse is lit"), and a derived flag for what its formula says, where that means something ("At least two of Abrecan, Godric and Rheda are in the party").
- **Never "Set when…", "Set by…" or "…while set".** They say how the flag is used, not what it means.
- **Nothing the tools work out from the data**: the journal entry a flag lists, that nothing writes it, what reads it. So "Defeated Shamsuk", whose flag lists entry 57; "Received journal entry *n*" only where the entry is all a flag means. A label that says what the data says goes wrong when a mod changes the data.
- **Places as a player calls them**, never a chunk's name, and none where the thing is unique: "Took Kendall's Hat", "Read the Yorwood remembrance sign". Where only the place tells two flags apart and the place is shared, its cell; then the object's index.
- **Plain verbs**: "Entered" a room, building or town, "Approached" something, "Returned to" a place, "Crossed" a bridge, "Reached" the top or end of something; "Talked to". People by name alone: "Met Edur and Yuli".
- **Nothing a player can't see**: no markers, coordinates or "book" after a book's title. The game's own names over descriptions (the Chaos camp, the Namer, Shamsuk's Tower), and proper names without "the" ("in Oisin forest").
- **A run of flags holding a number** is its name and the bit: "Day of the season, bit 0 of 6". The party's best stats keep theirs though nothing writes them ([below](#what-the-engine-writes)).
- **A flag nothing uses, or play never sets, has no label.** Naming it promises an event the game never brings about. If one turns out to be set after all, it gets a name then. Flags 0 and 1 are "Always clear" and "Always set".

### Which flags are used

A flag is used if anything writes it or something reads it other than a derived flag that's unused itself, and it can change if something writes it or it's derived from a flag that can. Of the 5,556, 2,376 are both and play can set them: 2,056 plain and 320 derived. Most of the rest are plain flags nothing in the data or the engine names, and derived flags nothing reads. 110 are used but play never sets them:

- **49 are read but can't change**: 46 plain flags nothing sets, among them the eleven journal entries that never show, the dryads' and the A05 goblins' leaving and Pandara's reward, and three derived flags over the party's best stats' never-written bits.
- **61 have setters that never run**, by the playthrough's static pass from a new game ([playthrough](playthrough.md)): 23 set only by scripts nothing starts (the door rhyme in Shamsuk's Tower, Shamsuk's letters, the joining scenes the [wanderers](wanderers.md) doc lists, the ending's farewells), 18 whose setters need a flag that's never set or never true (the Firelord's appearing, 4297; Phelan's errand, 5353), 4 set by objects gated off on flag 0, 9 containers' Used flags that are only ever cleared, and 7 derived flags that are never true. Where the pass's model falls short, the flags keep their names: the cheats and backdrops, which the story checkpoints show set. Camping ("Camped after raiding the goblin stronghold" and the camp talks), traps going off and the help menu, which code starts, the pass's model has had since the playthrough's stage 5 ([what the planner doesn't model](playthrough.md#what-the-planner-doesnt-model)). The list is `NeverSetInPlay` in the test.

**What play reaches.** The playthrough bot's flag coverage plays the game to set every flag the static pass calls reachable from a new game, over a tree of saves ([flag coverage](playthrough.md#flag-coverage)): 2,354 targets since stage 5 took in camping, traps going off, the help menu and the clock ([what the planner doesn't model](playthrough.md#what-the-planner-doesnt-model)), 2,230 of them seen set in play, and 2,263 flags in all. Every other flag is set by nothing in the data (2,907, most of them unused), by what the bot leaves out (deaths, the cheats the port hasn't ported, the party's best stats 1.0 never writes), or by setters that never hold. Stage 4's were 2,229, 1,881 plain and 348 derived, of which it saw 2,111 set, and 2,223 flags in all. Of the 118 it doesn't, the static pass is wrong about 6, which no play can set: the Barrows' five dragon flags (5509–5513, each a cut-scene done before its tripwire, whose radius takes the cut-scene's in) and Edur's npc talked to before his cut-scene (1349). 5 are 1.0's: Gwernia castle's farewells (600, 602, 603, 606, 609), enabled only by the coronation's 599, which comes with the ending's credits. The other 107 are the bot's ([what's left uncovered](playthrough.md#whats-left-uncovered)), most of them a party the bot doesn't make at the time. The dryads' battle flags 3654 and 3655 are set only by winning a fight the story means to be lost. The Shadow's encounter's 950 is set by nothing that plays: its battle is never won.

## The network

`FlagNetwork` holds every flag's value, by handle. A base-game flag's handle is its number, and other plugins' flags follow in load order (ADR 0004).

- **Reading.** Flag 0 always reads clear and flag 1 set. Reading a derived flag while anything has changed brings the network up to date first. Reading a plain flag doesn't. So the new journal entry flag, which the network sets, can lag until something reads a derived flag, as in the original ([below](#when-the-network-comes-up-to-date)). A map object's write is followed by such a read, so it brings the network up to date at once (`TrySetAndProcess`, [map objects](map-objects.md#map-objects-write-flags)).
- **Writing.** Only plain flags from 2 up can be set. Writes to 0, 1 and derived flags do nothing, as `setEventFlag` refuses them.
- **Unknown flags.** The rules read and write flags by record through `IsSet`, `Holds` (a map object's gate) and `TrySet`: a flag no loaded plugin has reads clear and its writes are ignored, since a mod can remove a flag another plugin's records still name, which the base game's never do. `Get(RecordId)` and `Set(RecordId, bool)` throw instead, for where an unknown flag is a mistake, as in tests.
- **Bringing it up to date.** Derived flags are evaluated in order, each one seeing those before it already updated. If any changed, it starts again from the first. 13 inputs name a later derived flag, so the order matters.
- **Formulas.** The inputs are read as bits, the first the lowest, or counted. Logic flags test all (AND), any (OR), exactly one (EOR), none (NOT), or the bits equal to the operand (MSK). Value and count flags compare with the operand by =, >, < or ≠. A kind with the other kind's operation reads as clear, since the original reports it as an error. No base flag does that, and none has an unused input (0xFFFF) or more than 9 inputs.
- **The journal.** When a flag that names a journal entry turns on, the new journal entry flag is set, and the entry becomes the one the journal opens at (`newestJournal`). In 1.0 that's `GameStateFunnel.Write` (`0x800cb33c`), which only `ProcessGameStates` (`0x800cb034`) calls for a derived flag: a write that turns on a flag above 5555 (`sltiu 0x15B4` at `0x800cb368`) sets 3617 (`+0x710e` in the table) and stores the entry's index, the flag less 5556 (`0x800cb380`; `FlagNetwork.SetNewestJournal`, `0x80020ea4`, into `0x800db05c`). Those flags are the last the network evaluates, each its entry's flag counted above 0, so an entry is added in the pass that brings the network up to date after its flag turns on. The port keeps one bit an entry flag in their place, as the network last saw the flag (`FlagNetwork.SeeJournal`): at the end of each pass, every entry whose flag has turned on since is added, in the entries' order, the last the newest. So the notice waits for the network as 1.0's does. The port also lists the entry in `JournalOrder`, the order the journal shows them in and a save keeps ([saves](saves.md#the-format)); one whose flag clears keeps its place. The journal lists an entry by its own flag, set or not in `JournalOrder` ([ui](pause-menu.md#the-journal)).
- **New games and loading.** A new game starts from the plain flags' initial values and evaluates the rest. `Restore` sets every plain flag at once and evaluates, as loading a save does. Derived flags and the journal's bits keep their old values until then, so any journal flag that turns on adds its entry again.

## When the network comes up to date

1.0 has no timer for it: `ProcessGameStates` runs only when a derived flag is read while the dirty halfword is set (`GameStateFunnel.Read`, `0x800cb3ac`, whose one caller is `FlagNetwork.Get`, `0x8001fd5c`), or when a game is loaded or begun (`GameStateFunnel.MarkAndProcess`, `0x800cb31c`). Trek writes the calendar's flags every frame, so the network is out of date nearly always, and only what happens to read a derived flag brings it up to date: outdoors that's nearly every frame, through the ambient sounds' gates, and in many rooms nothing. A journal entry's notice (`TrekLoop.JournalEntryNotice`, `0x80020eb0`) reads 3617, a plain flag, each frame with no fade, nothing queued, nothing busy and trek in its state 3, so **the notice comes on the first such frame after the network next comes up to date**, not after the flag is set.

`FlagNetwork.Get` has 40 callers, none through a pointer. These are the ones in trek and its scripts that can read a derived flag, which the port reads at the same places through `FlagNetwork.Get`, `IsSet` or `Holds`:

- **A map object's write** is followed by a read of 5626 ([map objects](map-objects.md#map-objects-write-flags)): a trigger, a Used flag, a container's opened or exploded flag, a secret door, a talker's flag B, with a flag in the slot or not (`setEventFlag` refuses 0, and the read comes anyway). So every trigger going off reads it, each tick the player stands in one. A door's picked and disarmed flags aren't followed by it, nor a chest's Used flag, written after its opened flag's read (`0x80017acc`).
- **Loading a chunk** reads each object's gate (`LoadedMap.Activate`, `0x80017af8`, through `MapObjects.Gate`, `0x800101e0`, and `VoxelObjects.GateTable`, `0x800da458`): flag C for most types, an npc's or encounter's A and B ([map objects](map-objects.md)). That's every chunk of the 3×3 when trek starts again after a cut-scene, a backdrop, the help menu or a battle (`InitGameTrek`), when the pause menu closes, on a teleport, and each new chunk on crossing a border. `LoadedMap.Activate` ports it. 1.0 also reads 5017 whenever Overworld A15 or Lighthouse A05 loads, and each time the 3×3 loads again while one is in it, to swap them to the lit lighthouse (`CheckToggleZoneScene`, `0x8000aa14`, [maps](../formats/maps.md)). The port reads it as 1.0 does, through the chunk's swap (`ChunkStreamer`); Draw Distance's ring reads it as it's stored.
- **Each tick,** the A gate of each active tangible teleporter, dialogue or trigger the player is within (`ProcessVoxelObjects`, `0x80083838`, through `MapObjects.Enabled`, `0x80010214`), but not while a script runs (`MapObjectUse.Touch`). So standing in the script object that started a cut-scene, gated by a derived flag as most are, brings it up to date on trek's first tick back.
- **A map sound** reads its gate every frame it's kept up and isn't playing, within its radius or fading out, before it looks at whether it needs starting (`Audio.UpdateSound`, `0x8004ea10`, then the bit at `0x8004ea24`; `KeptSound.Update`). More than a third of the sound objects are gated by derived 5283 (night) or 5284 (day), most of them repeating one-shots, which are silent most of the time between songs, and a loop reads it while its gate fails. So near most outdoor ambient sounds the network comes up to date nearly every frame, during a conversation too.
- **A script's `CheckFlag`** (`Dialogue.Condition`, `0x8004f680`, op 0x18). `SetFlag` and `ClearFlag` only write (`Dialogue.Effect`, `0x8004f7b8`, ops 0x20 and 0x21), and so do the done flag and the engine's writes for items and members ([scripts](scripts.md)).
- **A battle won** reads the npc or encounter's A gate after setting its encounter flag (`Combat.StateVictory`, `0x80022450`). The bosses' flags are set before it, as the battle is won, and again after it (`Combat.SetKillFlags`, `0x80067860`) ([combat](combat.md)). Where that gate is plain, as Kitarak's (154 itself) is, nothing in the battle brings the network up to date.
- **The journal** reads every entry's own flag as it opens (`Journal.AddEntry`, `0x8005256c`), and entry 32's is derived 5017 ([ui](pause-menu.md#the-journal)).
- Camping (`Camping.Ambushed`, `TrekLoop.CampScene`) and the end of a cut-scene, whose chain check reads script objects' A gates (`CutScene.Free`'s `MapObjects.Touches`).

The minimap's and the world map's flags, and the B gates `RenderVoxelScenes` reads as an actor's model loads, are all plain in the data, so they never do.

So after a cut-scene, a backdrop or a battle, an entry's notice comes as trek fades in where loading the 3×3, the dialogue the player stands in or a sound near him reads a derived flag, and otherwise waits. A conversation or a sign stays in trek and loads nothing: its entries come as it ends where a sound or a tangible object near the talker reads one, and otherwise wait, unless the script checks a derived flag after setting them. What the wait ends on is whatever reads one first: a chunk border, a tangible object, a container's or trigger's write, opening the journal, or leaving. None of it is the script's doing; nothing in the data sets a journal flag late on purpose.

Some entries wait long in 1.0, set where nothing near reads a derived flag: Kitarak's death (14), his boss flag, waits in his room in the Goblin Camp until its chest or the door out; the letter (35), a backdrop in the cave under Port Saiid, until its scroll (whose own entry, 30, comes in the same notice) or the way out; Tamberlain's four (44, 46, 50 and 53), at the inn in Terminor C05, until the door out. Of the conversations' entries, only Trahern's request (4) is followed by a `CheckFlag` of the script's own.

**The port tells every entry on trek's first tick with no fade, popup or conversation up after its flag turns on, the user's choice:** `TrekLoop` brings the network up to date just before it looks at 3617. What 1.0's timing hangs on is whatever happens to read a derived flag near the player, not the designers' choice; where they wanted an entry at a set moment they placed a trigger (the Wizard's School's, 216), which comes the same in both. So a conversation's entry is told as it ends, and a backdrop's, a cut-scene's or a battle's as trek fades in. The reads above still bring the network up to date where 1.0's do, which matters for what else derived flags gate. `GameSessionTests.Journal.cs` plays entries through both.

## What the engine writes

`StateFlags` writes numbers into runs of plain flags, lowest bit first, dropping bits that don't fit (`set_flag_array`). Every write marks the network out of date, even when nothing changes.

| Flags | What | Written |
| --- | --- | --- |
| 2299–2300 | Moon phase: 0 new, 1 crescent, 2 quarter, 3 full | Whenever time passes, which in trek is every frame |
| 2301–2303 | Part of the day: 0 morning (from 6:00), 1 midday (9:00), 2 afternoon (12:00), 3 evening (18:00), 4 night (21:00) | The same |
| 2304–2309 | Day of the season: week × 7 + day of the week | The same |
| 2310–2312 | Season, 0–5 | The same |
| 2313–2315 | Day of the week, 0–6 | The same |
| 2316–2318 | Week of the season, 0–7 | The same |
| 2319–2320 | Rain: 0 clear, 1 rain, 2 snow: what the weather has falling, or setting in, not what's drawn as it dies away ([weather](weather.md)). Fog is 0. | The same (`World.Update`, `0x8007bf5c`, through `StateFlags.SetRain`, `0x8001fe9c`) |
| 2321–2324 | The terrain type of the player's chunk | On entering a chunk of another terrain |

- **The terrain has four flags for 28 types**, so types from 16 wrap round.
- **The party's best stats and skills are never written.** Flags 2325–2369 are laid out for the party's best Intelligence, Willpower, Endurance, Dexterity, Strength, Mechanic, Diplomat, Loremaster and Wizard, and derived flags 5287–5346 compare them with thresholds. But `Event_flag_stat` and `event_flag_skill_`, which the original calls whenever a stat or skill changes, look the stat up in their table with a count of 0, so the lookup always fails and they return. None of these flags is set in any checkpoint. So in the original, the secret teleporter in EhudUnder M05 (needing Mechanic above 5) and three script objects in EhudUnder G03 (needing Loremaster above 4 or 5) never work. The port keeps that.
- **Darkness and Light** hold the part of the day in a battle, the original's lock at `World+5` ([weather](weather.md)). The port's hold is the battle's (`Battle.PartOfDay`, [magic](magic.md#where-the-port-differs)), and flags 2301–2303 go by the clock's hour alone. No checkpoint has the lock up.

## The ledger

The port's own, for the playthrough bot's [flag coverage](playthrough.md#flag-coverage): a `FlagLedger` on `FlagNetwork.Ledger` notes every flag that turns on, by handle. A plain flag is noted as it's written set (`Set`, and a run of bits from `SetBits` bit by bit), a derived flag as the network's evaluation turns it on, and the new journal entry flag as an entry raises it. So a flag set and cleared again before anyone looks still counts. A derived flag is seen only if the network comes up to date while it holds, as the game itself would see it. Loading a save and a new game set flags without noting them. The network marks only on a change to set, so the hot path, which trek's calendar takes every frame, is a null check. The ledger isn't saved, and outlives the network: `PlaythroughHost.Ledger` moves it to each game the host starts again on (a battle played again, a save loaded). `FlagLedgerTests` and `PlaythroughCoverTests` hold it.

## Checked against the checkpoints

`AresCheckpoint` (`HBHT.Rom.Rig`) reads the flags out of an ares state ([reference rig](../reference-rig.md)). In every story checkpoint, from 1.0 and the debug ROM, restoring the plain flags reproduces every derived flag, and the calendar, rain and terrain flags are what `StateFlags` writes from the state's clock, rain and terrain.
