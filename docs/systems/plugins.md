# Plugins: the format, loading and merging (Phase 5)

The importer writes the base with `HBHT.Plugins`' types, and the runtime and editor read every plugin through `PluginSet`. [ADR 0004](../adr/0004-record-ids.md) and [ADR 0005](../adr/0005-plugin-format.md) decide the format.

- **Load order** (`PluginSet.LoadOrder`): the base first, then `dependencies` first, `loadAfter` when that plugin is present, ties by ID. A cycle, or a folder not named for its plugin's ID, is an error.
- **Merging** (`MergePatch`) is RFC 7386 (a scalar replaces, an object merges, `null` removes), except that a **keyed list** merges element by element. The `[KeyedList]` attribute on a record property names the element's key fields; `RecordSchema` reads it, and the rest of the merge's knowledge of the types, from the serializer's metadata, so the merge and the record types can't drift. A patch element whose key the record has merges into it, one it lacks is added at the end, and `{ "index": 12, "$remove": true }` removes it. A list is keyed when something else names its elements by the key (a chunk's `objects` by `index`, a script's `nodes`, a map set's `spawns` by `portal`, and so on: grep `KeyedList`); a list whose elements' identity is their position, or whose elements repeat, is replaced whole. `KeyedListTests` checks the base's keys are unique. The script VM refuses a removed node, as it needs node *i* at position *i*; inserting and removing nodes is left to Phase 5 (ADR 0005). A record object's `$schema` is ignored, for editors.
- **The conflict report** (`PluginSet.Conflicts`, `hbht conflicts`, and a count in the editor's status line) lists every field that more than one plugin *patched*, by path (`damage`, `objects[12]`, `objects[12].position`, `minimap.rules`). The definer doesn't count. `PluginSet.Setters(id, path)` gives everyone who set a path, the definer first, which the editor shows per field.
- **Validation** (`PluginSet.Validate`). Reads are lenient (`PluginJson.Options`: a view such as `DbRecord` reads part of a record, and a save skips what it doesn't know), so a typo in a patch would merge and be ignored. `Validate` reads every record once with `PluginJson.Strict`, which refuses an unknown field or `type` discriminator, a null the type doesn't allow, a missing field with no default, and a keyed list with two elements of one key. `ValidationReport` blames each problem on the plugin that last set its path. Every problem is an error, in any plugin: a mod for a newer engine gets an honest refusal rather than a half-applied mod. `LoadInstalledChecked`, which the runtime and the CLI load by, throws the report; the editor (`RecordBrowser`) shows it and loads the records anyway, since it's where they're fixed. The runtime's check leaves out the base plugin's lazily indexed records that nothing has read (`Validate(unread: false)`, below): those are the importer's own, and the import reads the whole plugin back before it replaces the last one (`BaseImporter`), so a base record that doesn't read is the importer's error, found as it imports. Every mod's record is checked, and so is every base record a mod patches.
- **JSON Schema** (`RecordSchema.JsonSchema`, `hbht schema <dir>`): a draft 2020-12 schema per record type, exported from the strict options, so a schema refuses what validation refuses: `<type>.schema.json` for a record and `<type>.patch.schema.json` for a patch (every field optional and nullable all the way down, and `$remove` on keyed lists' elements). `SchemaRoundTripTests` checks a real record of every type against its schema.
- **Maps keyed by record ID.** A field that gives a value per stat, skill or element is a JSON object keyed by the record's ID (`{ "aidyn:skill/7": 3 }`: a sheet's `attributes`, `skills` and `weaponSkills`, an item's `requirements` and its bonuses' `stats`, `skills` and `resistances`, a body's `strikes`), which RFC 7386 merges key by key, so a mod adds its own skill or stat beside the base's without conflict (ADRs 0031–0033). `PluginJson`'s ID converter reads and writes the keys.
- **The record-type registry** (`RecordTypes.Registry`, ADR 0004) ties each type's name to its class, its key kind (`KeyKind`: `Db`, `Borg`, `Decimal`, `Chunk`, `MapObject`) and whether there's one of it; every other list of types is built from it. `RecordId.TryParse`, `Hex` and `Decimal` enforce the key's shape, so one record has one ID string. A type's records read as its class or a declared view (`DbRecord` for the four DB types: entities, spells, items and loot tables), and `Get`, `TryGet` and `All` refuse any other class. Scenes, textures, UI images, samples, animations, fills and collision have no class: they're assets alone. A chunk's key is its map set's number and its cell's name in the base game (`8/C05`, ADR 0035) and a name in a mod (`hermit_isle`); a map object's is its chunk's key and its index (`8/C05/17`, `hermit_isle/3`), in its chunk's namespace, so an object a mod adds to a base chunk by a patch has a base ID.
- **Rules over fields together** (`PluginSet.Rules`, in `Validate`): an item of kind `Weapon` needs its `weapon` fields and no other kind may have them (ADR 0031); an entity with no `sheet` can have no `combat`, `member` or `trainsFree` (ADR 0032); a script's or trigger's op runs only where its type can (`ScriptOp.Use`), a camera move names a mark or an actor, and only a trigger's condition has a range (ADR 0034); a base chunk's fields hold the cell its ID names, a teleporter has a `destination` or an `arrival`, and a `destination` beside an `arrival` is the arrival's chunk (ADR 0035).
- **Chunks by their cell** (`ChunkIndex`, ADR 0035). A map set lists no chunks: each chunk says where it is (`mapSet`, `row`, `column`), and `ChunkIndex.For(plugins)` finds the chunk in a cell (`At`), a map set's chunks (`In`), and a chunk's cell (`CellOf`); `plugins.ChunkAt` and `ChunksIn` read them. A base chunk's cell comes from its ID, so the index reads no file; a mod's from its fields. A mod adds a cell by adding a chunk. Two chunks claiming one cell: the earlier plugin's holds it, and `Validate` reports the later one, blaming its plugin.
- **Requests are played by number** (`Requests`, ADR 0004's handles): a base request's is its key, the original's number, and a mod's request gets a handle from 256 the first time it's asked for; handles never leave the process.
- **Reading records.** `PluginSet.Get`, `TryGet` and `All` read the merged JSON as a record type once and keep it, so every later call returns the same immutable object; nothing changes the merged JSON once the set has loaded, so the cache never goes stale and is safe from the audio thread. A singleton type (`aidyn:camping/0`, the sky, the sounds, the credits and the like) is read with `Singleton` or `TrySingleton`; a mod patches it rather than adding another.
- **How the records are written.** A field the importer leaves out means its default, which the record's comments name: a gate (`FlagGate`) left out always holds, a list left out is empty, a flag's `initial` is false. A field is optional only where leaving it out means something; nothing is optional for the sake of an older plugin, since `BasePlugin` refuses an out-of-date import. Fields nothing reads aren't written: the ROM's raw values stay in `hbht db` and the other dumps. A type with several shapes is polymorphic on `type`, as effects (ADR 0020), map objects and a tripwire's action (`does`) are; a script's or a trigger's ops are polymorphic on `op` (ADR 0034, [scripts](scripts.md#the-ops)), and `RecordSchema.DiscriminatorField` says which field a type's is in.
- **The base plugin's layout, and lazy loading** (ADR 0036). Most types are one file each under `records/` (`items.json`, `flags.json`); chunks and scripts are a file each, named for the record's key (`records/chunks/8/C05.json` is `aidyn:chunk/8/C05`, `records/scripts/0x0362.json` `aidyn:script/0x0362`), which a type's `RecordTypeInfo.LazyFolder` names. In the base plugin, `PluginSet` indexes those files by their path without reading them, and reads a record the first time anything asks for it (`Get`, `TryGet`, `GetJson`, `All`, `Validate`), once, under a lock, on whichever thread asks first: the chunk streamer's builder thread reads the next ring's (ADR 0025). `IsRead` says whether it has been; `Contains`, `Ids` and `IdsOf` list it either way. A file there that holds another record than its path names is refused as it's read. A mod's patch to such a record reads it as the patch loads, so the merge and the conflict report are as before. Mods' records load eagerly, in any layout: a file holds one record or an array of them, wherever it is under `records/`. A checked load of the base plugin takes about 0.6 s where it took 1.9 (the cache 0005 planned isn't needed for it).
- **Lua files** go in a plugin's `lua/` folder, kept for Phase 5's Lua (ADR 0008). Nothing loads it yet; the `lua` effect and the `lua` op name a file there and a function in it, and load as reserved: they do nothing, and are reported.
